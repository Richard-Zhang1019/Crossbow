# 轻量退出后的内核守护：复现证据与方案边界（#601 工作包 F）

状态：复现完成 + 方案边界定稿（2026-11-21，macOS 实测）。守护实现独立 PR，不含在本文件。

## 一、复现证据（macOS，系统代理模式，v0.15.2 正式签名版）

基线：GUI PID 18038 / 内核 PID 18849 / 系统代理 127.0.0.1:7898 开启 /
经代理请求 HTTP 204（0.41s）。

说明：托盘菜单项无法被无头 UI 自动化触达（NSStatusItem 不在
AXExtrasMenuBar 枚举面），轻量态用 **SIGKILL GUI 进程**构造——该状态与
轻量退出后的守护缺口完全一致且更严苛（连优雅 detach 都不存在）；
内核描述符已在磁盘（start 时写入），代理黑洞的成因与持续性与真实
轻量退出相同。

| 时点 | 动作 | 观测 |
| --- | --- | --- |
| T0 | `kill -9` GUI 进程 | GUI 退出；内核 18849 存活；sysproxy 仍开启；经代理请求 **HTTP 204**（轻量态成立：代理继续可用） |
| T1 | `kill -9` 内核（模拟轻量期崩溃） | 内核死亡；**sysproxy 仍指向 127.0.0.1:7898** |
| T+2s | 经代理请求 | **HTTP 000 connection refused —— 代理黑洞确认** |
| T+62s | 复查 | sysproxy 仍开启（**无自愈**，应用侧崩溃还原回调已随 GUI 消失）；黑洞持续 ≥60s |
| T+~90s | 外部干预：重新打开应用 | adopt 失败（内核死）→ `clear_stale_system_proxy_early` 自愈 → 冷启动新内核 → sysproxy 指向新内核 → **HTTP 204** |

结论：黑洞持续到「应用重新打开」或「用户手动关闭系统代理」，与 issue
预估一致。期间所有走系统代理的应用流量全部失败。附带验证：内核死亡
后重开应用，自愈 + 冷启动链路工作正常（验收第 3 条相关）。

本轮未测：睡眠唤醒、切网场景（需物理网络变更，待实机）；TUN 模式
（TUN 由内核自身接管，轻量期 TUN 崩溃的表现待专项复现）。

## 二、方案边界（守护实现 PR 的约束）

**承担**（最小低资源守护）：
1. 轻量退出时登记轻量会话（描述符已持久化 + sysproxy 快照已持久化）；
2. 周期探活：内核 PID（含二进制身份比对）+ 混合端口监听状态；
3. 内核死亡且 sysproxy 归属仍为本应用时：**仅恢复系统代理**（按 journal
   快照走既有还原通道），通知用户 + 记录日志；
4. GUI 重新启动收养时守护让位（收养成功即注销轻量会话）。

**不承担**：
- 不自动重启内核（issue 明确禁止无边界自动重启；重启 = 用户重开应用）；
- 不覆盖第三方代理：恢复前检查系统代理指向必须仍是本应用记录的
  host:port，第三方改写后不动；
- 不重开用户已关闭的接管（TUN/系统代理开关状态以用户最后一次操作为准）；
- 不暗示应用退出后订阅调度/统计/通知等仍在运行（守护只管「不残留死代理」）。

**形态候选（实现 PR 时定）**：macOS 用户级 LaunchAgent（GUI 退出后由
launchd 拉起小型守护做探活，资源占用 < 10MB 常驻）；Windows 复用服务
体系思路；Linux 复用既有 service 体系。守护与 GUI 通过描述符 + 轻量
会话标记协调，避免双写。

**保留的既有检查**：PID/二进制身份（`process_matches_binary`）、系统代理
归属（journal 快照比对）、退出/更新交接协调（`prepare_handoff` /
`update_handoff`）——守护不得绕过这些检查径自动作。
