# 桌面验收：可复跑场景与实机记录

本文回答两个问题：**下次怎么用同一条命令复跑关键桌面场景**，以及**某个版本在真实机器上验收到了哪一步**。
模拟结果与原生结果按 [QUALITY.md §5](QUALITY.md) 分开记录，不相互替代。

## 1. 可复跑入口（模拟环境）

```sh
pnpm install --frozen-lockfile       # Node.js 22+、pnpm 9
pnpm verify:desktop                 # 全部场景（headless）
pnpm verify:desktop --scenario 2   # 只跑一个场景
pnpm verify:desktop --headed       # 显示浏览器
```

- 工作方式：vite dev 按生产代码原样渲染页面；`addInitScript` 注入
  `__TAURI_INTERNALS__` 桩（`scripts/dev/verify-lib.mjs`），IPC 夹具由场景通过
  `window.__cb` 控制迟到、失败与事件顺序。playwright-core 只驱动系统已装浏览器
  （`CB_CHROME_BIN` 可指定），不下载浏览器二进制。
- Vite 使用临时回环端口和独立缓存。模拟页面只允许连接该回环服务，夹具不调用真实订阅、内核、系统代理或 TUN。
- 未注册 IPC、页面异常和非回环请求会让场景失败。失败记录包含场景、提交、浏览器版本、视口、截图、IPC 计数和控制台错误。默认写入系统临时目录，可用 `CB_VERIFY_ARTIFACTS_ROOT` 指定目录。
- CI 在纯前端改动时用 frontend 作业，在同时有 Rust 和前端改动时用 Linux foundation 作业。两条路径共用命令，失败时上传 `desktop-scenario-evidence`。原生验收单独记录。

### 场景清单

| # | 场景 | 驱动点 | 固化的回归 |
| --- | --- | --- | --- |
| 1 | 配置快切忽略同名节点旧结果 | 从页头切换配置，新快照渲染后释放旧测速应答 | 同名节点保留新快照延迟，后端收到结束旧任务的请求 |
| 2 | 测速取消后停止派发 | 测速期间等待周期刷新，释放第一批、取消，再释放迟到结果 | 刷新后继续派发，取消后派发数冻结，已完成结果与未完成的取消状态保留 |
| 3 | 诊断原样本和恢复样本及导出白名单 | 故障证据、过期与复检事件、预览与复制按钮 | 两种故障状态正确展示，复制结果与白名单摘要一致 |
| 4 | 默认和最小窗口的焦点与滚动 | 使用 Tauri 配置的两种尺寸，遍历中英文和明暗主题的八种组合 | 导航可点，页脚可见；Tab 到端口编辑时滚动到视口，Enter 打开，Escape 恢复焦点 |

中英文与明暗主题经 `ui://lang` / `ui://theme` 事件热切换（设置页同一路径），无需重载。

### 2026-11-16 · 关窗后台恢复 + 恢复前换核 superseded（实机，#505/#502 部分）

- 提交/构建：本地 `tauri build --no-bundle`（main `2590924`）；已装 v0.14.4 作对照
  （无金丝雀功能——该功能随 #505 入 main，晚于 v0.14.4 发版）。
- 平台：macOS 27.2 arm64（Apple M2）；内核：mihomo v1.19.32（应用托管）。
- 代理模式：系统代理接管（混合端口 7898，Wi-Fi + Thunderbolt Bridge 双服务），
  TUN 关闭；真实出口（用户日常节点）。
- 操作：关闭主窗口进托盘待机 → `SIGSTOP` 内核注入代理超时（超时类故障；
  TLS 失败类未做实机注入，模拟已覆盖）→ 等金丝雀捕获（120s 节奏）→ `SIGCONT`
  → 等恢复记录 → 重开主窗口核对诊断页故障卡。变体：二次故障捕获后、恢复前
  `kill -9` 内核（上下文变更）→ 验证 superseded。
- 预期出口：故障证据含主探针超时 + 独立复核超时、直连基准双 204（定位故障在
  代理层）、恢复探针 204、系统代理指向逐服务记录、无凭据泄露；变体中旧故障
  标记 superseded 不被误标恢复，previous 保留可展开。
- 结果：通过。STOP 12:10:51 → 捕获 12:12:11（primary/review 均 timeout）→
  CONT 12:12:31 → 恢复 12:14:13（ok/204）；重开后诊断卡与文件证据逐字段一致
  （窗口截图核对）。变体：二次捕获 12:27:55 → kill 12:28:05 → 换核后下一轮
  金丝雀将 latest 标记 superseded=True（resolved 保持 None），previous（已验证
  恢复）保留。CONT 后首个请求失败约一次（冻结期上游连接被对端断开），数秒内
  自愈——已知语义，与证据模型一致。
- 与模拟覆盖差异：本次为真实内核 + 真实系统代理 + 托盘待机 + 真实出口流量；
  未覆盖：真实 Wi-Fi↔热点切网、睡眠唤醒、IPv6-only（#502 主服务识别缺口待修）、
  双接管、Windows。
- 附带实测缺陷（已立 issue）：#518 收养内核死亡不自愈且重启陷入收养循环；
  #519 退出恢复系统代理触发管理员授权弹窗并阻塞退出。恢复服务时确认：手动
  spawn 内核 + 写入描述符后应用可正常收养（收养装配路径可用）。

### 2026-11-16 · 睡眠唤醒恢复（实机，#502 第一轮）

- 提交/构建：同上窗口（本地 `tauri build --no-bundle`，main `2590924`）。
- 平台/内核/代理模式：同上（系统代理接管 7898，TUN 关）。
- 操作：锁屏合盖睡眠数分钟 → 唤醒后不开窗口直接访问代理站点（第一轮）；
  再次锁屏合盖 → 唤醒后打开主窗口（第二轮）。
- 预期出口：唤醒后代理自动恢复；故障证据正确记录唤醒期失败；无 webview
  崩溃。
- 结果：通过。第一轮故障证据精确对应体感：主探针 TLS 失败（16:12:59，唤醒
  期网络栈恢复中）→ 独立复核 ok（16:13:17）→「采集时代理路径可达」自动恢复
  （约 18 秒，用户体感「十几秒」）。第二轮主窗口白屏 3-4 秒后 UI 正常、代理
  可用；webview 心跳无 >5s 间隙、无 JS 错误——定性为待机销毁后窗口重建 +
  唤醒期冷渲染耗时（观察项：若日常非唤醒场景复现白屏再立 issue）。
- 附带确认：15:39 双 TLS 失败旧记录（服务手动恢复期间捕获）被正确标记
  superseded，未污染当前态——上下文变更语义在唤醒场景同样成立。
- 剩余：唤醒双接管、切网矩阵（Wi-Fi↔热点/有线）、事件密集与第三方 VPN/
  PAC/登录门户场景待验。
