# #632 导入成功通知移除「选择节点」· v01

日期：2026-11-22 · 关联 issue：#632 · 状态：已实现，待 PR 评审

## 问题

激活订阅 A 时导入 B，成功通知带「选择节点」动作；点击后进入节点页，看到的是仍然生效的 A，
不是刚导入的 B。用户可能误以为 B 已激活并继续修改 A。

## 决策（用户已明确）

直接移除这个跳转，**不**通过自动激活新订阅让按钮"看起来正确"——那会改变正在使用的代理配置和业务流量。

## 改动

- `apps/desktop/src/pages/Profiles/index.tsx`：导入成功的通知只在**首次导入**（`activeProfileId` 为 `null`）
  保留 `continueSetup` 设置引导，其余情况（已有激活订阅、读取失败得到 `undefined`）都不再附带任何动作。
- 其它导入入口（URL、文件/拖放、粘贴、多文件）都经由同一 `importProfiles`，行为一致；
  深链导入在 Rust 侧独立处理，本就只用 `ContinueSetup`，未改动。
- 通知历史是会话内存态（不落盘），升级后不存在需要迁移的旧记录，因此没有加入历史过滤逻辑。

## 证据

- `scripts/dev/verify-import-notification.mjs`（生产组件 + 脱敏 IPC）覆盖三条路径：
  1. 有激活订阅 + 导入 → 成功通知 `actions=[]`，未调用 `set_active_profile`，页面仍停在配置页；
  2. `activeProfileId` 读取失败 → 同样没有动作；
  3. 首次导入（无激活配置）→ 仍带 `continueSetup`。
- 改前/改后截图：同一生产组件、同一 IPC 夹具，改前把发布出去的通知放进通知中心可见「选择节点 →」，
  改后该动作消失（`previews/before.png` / `previews/after.png`）。
- 既有的 10 个桌面场景全部通过；`verify-lib` 新增静默命令参数记录（`payloads` / `payloadLog`），
  供场景断言"发了什么"而不只是"发了几次"。
- 场景已登记进 `build.yml` 两处固定清单（用户已放行与 #631/#633 并行修改）。

## 未覆盖

- 安装版真实点击与通知中心交互（用生产组件 + IPC 桩验证，未启动真实内核）。
- 托盘/系统通知中心路径：本修复只影响通知载荷里的动作，不改变托盘提示的触发条件。
